# v0.4.0 — Derive a libc-clock link overlay without rewriting ABI evidence

Consumers can explicitly request a one-library overlay that selects libc clock defaults while retaining librt compatibility versions and every other byte.

Original registry publication date (UTC): **2026-11-02**. Source tag
[`v0.4.0`](https://github.com/rustcommons/linux-abi-tools/tree/v0.4.0), commit
[`7ce231df7128582a355c2dce47ae6436364d5e88`](https://github.com/rustcommons/linux-abi-tools/commit/7ce231df7128582a355c2dce47ae6436364d5e88).
All five workspace packages were published at 0.4.0; all five are non-yanked as
verified on 2026-11-02. This is a crate release, not a source-only historical tag.

These notes were reconstructed on 2026-11-02 and were not part of the original

the documentation backfill date, not the original registry publication date.

## Changes

- `libc_abi_tools::provider::link_profile` adds `prepare`, `LinkProfile::LibcClocksV1` and `Overlay` for actual selected libc/librt ELF files. The five clocks use libc GLIBC_2.17 defaults; applicable librt GLIBC_2.2.5 definitions become compatibility-only in a copy. Already compatible inputs return no overlay.
- ELF validation rejects conflicting partial/load-page/zero-fill mappings. A content/policy-bound manifest index uses standard-library hard-link publication without replacing existing files/directories; concurrent losers verify the winner and clean only their unpublished generation.
- Ordinary rendering/providers, raw tables, descriptor v1 and linker argument order remain unchanged. There is no new CLI clock knob or unwinder/runtime implementation. All five packages share 0.4.0 under the lockstep API-addition policy.

## Upgrade

Library consumers need a 0.4 `libc-abi-tools` requirement for the new API; 0.3.3 does not provide it. Automatic Cargo use needs the companion integration, rather than changing an already installed consumer. Callers select/contain the actual ELF inputs and perform identity-checked same-position substitution or refusal for explicit paths/scripts. Cache roots must support same-filesystem hard links. The existing documented file/symbol limits and x86_64 GNU/Linux scope still apply.
