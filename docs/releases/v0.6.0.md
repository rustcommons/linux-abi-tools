# linux-abi-tools workspace 0.6.0

Release candidate prepared 2026-11-08 UTC; **not published**. All five producer
crates move together to 0.6.0. This is separate from the already published
cargo-libc 0.6.0, which does not yet contain the provider-cache repair.

## Changes

- Provider preparation publishes complete immutable generations through an
  atomic regular-file selector. `prepare --force` no longer removes or rewrites
  directories already returned to builds. Concurrent normal writers retain one
  winner; forced writers may each return a complete generation, with the last
  successful selection becoming current. Failed/losing attempts clean up only
  their own unpublished data.
- Exclusively created staging names prevent same-process preparations from
  deleting each other's work. Discovery, import/export and explicit removal
  understand the generation layout. Targeted operations filter release/mode
  before resolving selectors, so unrelated corrupt entries do not block them.
- Add public `provider::cache::current` to resolve the actual selected entry.
  Descriptor v1, exported logical layout and legacy-directory discovery remain
  supported. Other workspace crate implementations are unchanged.

## Upgrade

This API/cache contract requires a minor version under the lockstep policy.
Use paths returned by `prepare`, `path`, `list`, `import` or `cache::current`;
do not reconstruct a physical cache directory from a hash. `cache::entry`
constructs a logical legacy base, not a generation lookup. Invalid selection
metadata refuses without silently falling back to a legacy directory.

Old generations consume disk until explicit removal. Stop builds and other
cache operations before `provider remove` or manual deletion. Saved plain-Cargo
settings and explicit descriptors stay bound to their original generation;
regenerate settings or select the new returned path to switch. Changed paths
can cause rebuilding even when the preparation input hash is unchanged.

The root crate version participates in provider-cache input identity. Upgrading
to 0.6.0 can require a fresh preparation under a new key; old/imported providers
are not an automatic offline migration path. Retain required GCC/binutils and
embedded inputs for source mode. Container preparation additionally needs its
engine/image and potentially archives/network, and still uses host startup
inputs. Host GCC startup files outside the generation remain independently managed.

Publish targets, kernel, scanner, libc tools, then umbrella. Downstream
cargo-libc must deliberately raise its libc-abi-tools minimum to published 0.6.0
and validate a real registry lock/install. A source patch or lock-only update
does not enforce a minimum. Keep its other tool minima/locks unchanged unless
separate evidence requires changes. Consumer version choice and release remain
separate gates; equal producer/consumer version numbers are not a policy.

MSRV 1.90, native-tool floors, upstream glibc requirements/locked 0.1.0 inputs,
raw ABI/source data, kernel profiles, clock policy and the system unwinder are
unchanged. No LLVM replacement or prebuilt delivery is included.

## Validation and limits

The implementation merged as `baf407084ea0d6a6b8fdfeb7d0ef9f79956429f9`
after independent review. The reviewer verified 120 proof hashes, five source
archives and 15 focused Rust 1.90 filesystem/cache/CLI tests. Earlier owner
Windows/Linux tests, all-28 source-provider lifecycle checks and real multi-process
read/write tests passed. Installed cargo-libc 0.6.0 built and ran C/CMake using an
old descriptor after a forced new generation. The dated record preserves exact
scope and the deliberately interrupted preliminary debug gate.

Exact 0.6.0 candidate workspace, package and version/cache-identity checks are
tracked in the preparation record; results are pending at this preparation commit.
Registry publication, official archive/VCS/tag/docs.rs and downstream adoption
are separate later gates. No candidate is described as published or release-complete.

Use a caller-controlled local filesystem with hard links and atomic file
replacement. There is no automatic GC, destructive-removal lease, authenticated
delivery, crash-durable transaction or distributed-filesystem guarantee. Manual
edits, older binaries and filesystem failures are not coordinated. Windows
filesystem tests do not establish Windows provider-preparation support.
Real-container rebuilds, old-OS/kernel/tier 3 and musl/static-host qualification
are not newly claimed. Existing optional clock-profile gates retain their prior
scope/ignores. Legal review still gates prebuilt providers.
